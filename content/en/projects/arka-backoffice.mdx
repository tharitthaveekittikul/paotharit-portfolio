ARKA's Bangkok clothing store ran on spreadsheets. Stock counts were unreliable, purchase orders lived in chat threads, and product returns were handled manually in LINE. I built ARKA Backoffice to replace all of it — a full-stack web system with real-time stock tracking, QR-code fulfillment for warehouse staff, supplier purchase orders, cost analysis, and a role-based access system with an immutable audit trail.

## About ARKA

[ARKA](https://www.instagram.com/arka.bkk/) is a Bangkok women's clothing store selling across Instagram, Shopee, TikTok, and Lazada. The store is run by a small team and as order volume grew, spreadsheet-based operations started introducing errors — stock counts nobody trusted, purchase orders tracked in chat, returns handled by hand.

## The Problem

Before the backoffice existed, everything was manual:

- **Stock**: Counts lived in spreadsheets, updated by hand after each sale or restock. No history, no audit trail.
- **Purchase orders**: Created in chat messages and documents. No structured tracking, no shipment status.
- **Product returns**: Customers messaged LINE, staff recorded exchanges manually.
- **Employees**: No access control — whoever had the spreadsheet link could edit everything.
- **Financials**: COGS, landed costs, and cashflow had to be calculated separately after the fact.

## Stock Management

The core feature. Every variant's current stock is computed as the sum of its `stock_transactions` — an append-only ledger where each row records a quantity movement. No row is ever updated or deleted; Supabase RLS enforces this at the database level.

For fulfillment staff on the warehouse floor, stock-in and stock-out run through a mobile-optimized PWA — installable from the browser, no app store required. The stock-in flow:

1. Open `/stock/in` on mobile
2. Scan the QR code on the product label → SKU auto-fills
3. Enter quantity → submit
4. A `stock_transaction` row is created immediately

Stock out follows the same pattern on `/stock/sale`. The QR code encodes the SKU directly so staff can also type it manually if scanning fails.

## Supplier Orders & Shipment Batches

Purchase orders record what was ordered from each supplier — style, color, size, quantity, and unit price. When goods arrive, a shipment batch captures the actual quantities received against the PO. Discrepancies (short shipment, overdelivery) are flagged for review.

Landed cost calculation rolls in the supplier price, freight, and import/export tax duties to produce a true COGS per unit. This feeds directly into the cost analysis view.

## Product Returns

When a customer needs to return or exchange an item, they fill out a Tally form. A webhook fires to `/api/webhooks/tally-return`, which parses the submission and creates a return record in Supabase. Staff can print a return label directly from the return detail page.

## Access Control

Four roles govern what each user can do: **Developer Admin**, **Owner**, **Employee**, and **Fulfillment Employee**. Permissions are action-level — not just page visibility. A Fulfillment Employee can record stock-in and stock-out but cannot view financials, manage products, or access the audit log.

## Audit Log

Every create, update, and delete action — including role changes, product edits, and stock entries — is recorded as an immutable row in `audit_log`. RLS at the database level blocks UPDATE and DELETE on the table entirely. When something goes wrong, the owner can trace exactly who did what and when.

## Lessons for Business Tool Builders

1. **WORM audit trail from day one.** You will never regret it; you will regret not having it the first time an employee edits the wrong record. Append-only enforced at the database level, not in application code.

2. **QR codes with human-readable SKUs.** Staff can read the label if the scanner fails. `JN02-DF-M` is far more useful than a UUID in a warehouse.

3. **RBAC should be action-level, not page-level.** "Can see this page" is a weak guarantee. Supabase RLS plus server action checks enforce it where it actually matters — at the data layer.

4. **PWA over native app for internal tools.** No app store approval, no cross-platform overhead, updates deploy instantly. Fulfillment staff just bookmark the URL and install it from the browser.

5. **Append-only ledger for stock.** Derived state (current stock = SUM of transactions) is easier to audit and recover from than a mutable counter. The performance cost at this scale is zero.
