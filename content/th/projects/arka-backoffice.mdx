ร้าน ARKA ในกรุงเทพฯ บริหารงานด้วย Spreadsheet มานาน นับสต็อกผิดพลาดบ่อย ใบสั่งซื้อกระจัดกระจายอยู่ในแชท และจัดการการคืนสินค้าเองผ่าน LINE ทั้งหมด ผมสร้าง ARKA Backoffice ขึ้นมาแทนที่ทั้งหมดนั้น — ระบบเว็บเต็มรูปแบบ ตรวจสต็อกแบบเรียลไทม์ด้วย QR Code, จัดการ Purchase Order, วิเคราะห์ต้นทุน, และระบบสิทธิ์แบบ RBAC พร้อม Audit Trail ที่ไม่สามารถแก้ไขย้อนหลังได้

## เกี่ยวกับ ARKA

[ARKA](https://www.instagram.com/arka.bkk/) คือร้านเสื้อผ้าผู้หญิงในกรุงเทพฯ ที่ขายสินค้าผ่านหลายช่องทาง ได้แก่ Instagram, Shopee, TikTok และ Lazada ทีมงานมีขนาดเล็กและเมื่อยอดออเดอร์เพิ่มขึ้น การทำงานด้วย Spreadsheet เริ่มสร้างความผิดพลาด — สต็อกที่ไม่มีใครไว้ใจได้, PO ที่ติดตามผ่านแชท, และการคืนสินค้าที่ทำเองด้วยมือ

## ปัญหาก่อนมีระบบ

ก่อนที่ Backoffice จะมีอยู่ ทุกอย่างทำด้วยมือ:

- **สต็อก**: อยู่ใน Spreadsheet อัปเดตด้วยมือหลังขายหรือรับของ ไม่มีประวัติ ไม่มี Audit Trail
- **ใบสั่งซื้อ**: สร้างในแชทและเอกสาร ไม่มีการติดตามเป็นระบบ ไม่รู้สถานะการขนส่ง
- **คืนสินค้า**: ลูกค้าส่งข้อความใน LINE พนักงานบันทึกเองทั้งหมด
- **พนักงาน**: ไม่มีการควบคุมสิทธิ์ ใครมีลิงก์ Spreadsheet ก็แก้ไขได้
- **การเงิน**: ต้นทุนสินค้า, Landed Cost และ Cashflow คำนวณแยกออกมาเองหลังจากนั้น

## การจัดการสต็อก

ฟีเจอร์หลักของระบบ สต็อกปัจจุบันของแต่ละ Variant คำนวณจากผลรวมของ `stock_transactions` ทั้งหมด — เป็น Append-Only Ledger ที่แต่ละ Row บันทึกการเคลื่อนไหวของจำนวน ไม่มีการแก้ไขหรือลบ Row ใดๆ โดย Supabase RLS บังคับใช้ที่ระดับฐานข้อมูล

สำหรับพนักงานคลังสินค้า การรับและจ่ายสต็อกทำผ่าน PWA ที่ Optimize สำหรับมือถือ — ติดตั้งได้จากเบราว์เซอร์โดยไม่ต้องผ่าน App Store ขั้นตอนการรับสต็อก:

1. เปิด `/stock/in` บนมือถือ
2. สแกน QR Code บน Label สินค้า → SKU จะกรอกให้อัตโนมัติ
3. ใส่จำนวน → กด Submit
4. Row `stock_transaction` ใหม่จะถูกสร้างทันที

การจ่ายสต็อกใช้ขั้นตอนเดียวกันที่ `/stock/sale` QR Code เข้ารหัส SKU โดยตรงเพื่อให้พนักงานพิมพ์เองได้หากสแกนไม่ได้

## Purchase Order และ Shipment Batch

Purchase Order บันทึกสิ่งที่สั่งซื้อจากแต่ละซัพพลายเออร์ — Style, สี, ไซส์, จำนวน และราคาต่อหน่วย เมื่อสินค้ามาถึง Shipment Batch จะบันทึกจำนวนที่ได้รับจริงเทียบกับ PO ความไม่ตรงกัน (ขาดหรือเกิน) จะถูก Flag ไว้สำหรับตรวจสอบ

การคำนวณ Landed Cost รวมราคาซัพพลายเออร์, ค่าขนส่ง และภาษีนำเข้า/ส่งออก เพื่อคำนวณต้นทุนที่แท้จริงต่อหน่วย ซึ่งใช้ในการวิเคราะห์ต้นทุนต่อไป

<Callout type="note">
  ภาพหน้า Purchase Order, Shipment Batch และภาษีส่งออกกำลังจะมาเร็วๆ นี้
</Callout>

## Audit Log

ทุก Action ที่ Create, Update และ Delete — รวมถึงการเปลี่ยน Role, แก้ไขสินค้า และบันทึกสต็อก — จะถูกบันทึกเป็น Row ที่แก้ไขไม่ได้ใน `audit_log` RLS ที่ระดับฐานข้อมูลบล็อก UPDATE และ DELETE กับตารางนี้โดยสมบูรณ์ เมื่อมีปัญหาเกิดขึ้น เจ้าของสามารถย้อนดูได้ว่าใครทำอะไรและเมื่อไหร่

## บทเรียนสำหรับผู้สร้าง Business Tool

1. **WORM Audit Trail ตั้งแต่วันแรก** คุณจะไม่เสียใจที่มี แต่จะเสียใจมากถ้าไม่มีในวันที่พนักงานแก้ไข Record ผิด Append-Only ที่บังคับใช้ที่ระดับฐานข้อมูล ไม่ใช่แค่ใน Application Code

2. **QR Code ที่มี SKU อ่านได้ด้วยตา** พนักงานอ่าน Label ได้ถ้าสแกนไม่ได้ `JN02-DF-M` มีประโยชน์กว่า UUID มากในคลังสินค้า

3. **RBAC ควรทำงานระดับ Action ไม่ใช่แค่ระดับหน้า** "มองเห็นหน้านี้ได้" เป็นการรับประกันที่อ่อนแอ Supabase RLS บวก Server Action Checks บังคับใช้ที่จุดที่สำคัญจริงๆ คือที่ Data Layer

4. **PWA แทน Native App สำหรับ Internal Tool** ไม่ต้องผ่าน App Store, ไม่มี Cross-Platform Overhead, อัปเดต Deploy ได้ทันที พนักงานแค่ Bookmark URL แล้วติดตั้งจากเบราว์เซอร์

5. **Append-Only Ledger สำหรับสต็อก** Derived State (สต็อกปัจจุบัน = SUM ของ Transaction) ตรวจสอบและกู้คืนได้ง่ายกว่า Counter ที่แก้ไขได้ ที่ Scale ระดับนี้ Performance Cost เป็นศูนย์
